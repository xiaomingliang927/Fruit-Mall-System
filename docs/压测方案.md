# fruit-mall 后端压测方案

> 适用环境：本机开发环境（Windows + 本地 MySQL 3307 + Spring Boot 3 单实例 :8080，无 Redis / 无 Docker）。
> 基础：已有 `OversellConcurrencyTest`（100 线程抢 50 库存，乐观锁防超卖）+ 12 个集成测试类（53+ 用例全绿）。

## 一、目标

1. **正确性优先**：高并发下不超卖、不脏数据（超卖数必须 = 0）。
2. **容量基线**：得出当前单机（无缓存）下各核心接口的 TPS、P95/P99 延迟、错误率。
3. **瓶颈定位**：明确第一个瓶颈点（预判为 HikariCP 连接池，见「已知瓶颈预判」）。
4. 产出压测报告（TPS 曲线 + 阈值结论），作为后续引入 Redis 缓存/连接池调优的对照基线。

## 二、接口分级与压测场景

| 级别 | 接口 | 路由 | 压测场景 |
|---|---|---|---|
| L0 只读热路径 | 商品列表 | `GET /api/v1/products?page=1&size=10` | 浏览刷列表 |
| | 商品详情 | `GET /api/v1/products/{id}` | 详情页连点 |
| | 分类 | `GET /api/v1/categories` | 首屏并发 |
| | banner | `GET /api/v1/banners` | 首屏并发 |
| L1 用户读写 | 购物车 | `GET /api/v1/cart`、`POST /api/v1/cart/items`、`PUT /api/v1/cart/items/{itemId}` | 加购/改数量 |
| L2 交易关键路径 | 下单扣库存 | `POST /api/v1/orders`（body：`{addressId, items:[{skuId, quantity}]}`） | 秒杀型并发 |
| | 订单列表/详情 | `GET /api/v1/orders`、`GET /api/v1/orders/{orderNo}` | 我的订单轮询 |
| L3 需限流保护 | 登录发码 | `POST /api/v1/auth/sms-code`、`POST /api/v1/auth/sms-login` | **小流量验证即可，不重压**（短信/验证码是外部资源语义） |

- 鉴权：`Authorization: Bearer <token>`，token 通过 `POST /api/v1/auth/sms-login`（开发万能码 `123456`）获取。
- L2 秒杀场景直接复用 `OversellConcurrencyTest` 的不变量断言思路：N 并发抢 M 库存（N > M），最终售出 = M、库存 = 0、不超发。

## 三、工具选型（本机约束：无 Docker / 无 Redis）

### 方案 A（首选，零安装，现在就能跑）：纯 Java 压测测试

在 `backend/src/test/java/com/fruitmall/load/` 下写 `@SpringBootTest` 压测类，用 `CountDownLatch` + 线程池并发调用 `*Service`（直接打 Service 层，绕过 HTTP，验证业务与 DB 层容量）或 `TestRestTemplate`/`WebClient`（打 HTTP 层更真实）。

- 优点：与现有 53+ 集成测试同框架，`mvn test -Dtest=Load*` 一条命令，CI 可复跑，无需安装任何东西。
- 缺点：压测客户端和服务端同进程同机，CPU 互相挤占，数据只能作**相对基线**，不能对外宣称绝对 TPS。
- 已有范式：`OversellConcurrencyTest`（CountDownLatch 起跑 + AtomicInteger 计数 + 不变量断言）可直接照抄扩展。

### 方案 B（推荐二期引入，更接近真实）：k6

k6 是单二进制（约 40MB，无 Docker 依赖），下载解压即用：https://k6.io/open-source/ 。

- 优点：对运行中的 `:8080` 发真实 HTTP；自带阶梯加压（stages）、P95/P99、TPS 统计、错误率分组（`group()`/`tag()`）；JS 脚本好维护。
- 本项目已备好脚本：`scripts/loadtest/fruit-load.js`（含 4 组场景 + 阶梯加压 + token 登录复用），k6 装好后：
  ```bash
  k6 run scripts/loadtest/fruit-load.js --env BASE=http://localhost:8080 --env SMOKE=1
  ```
- 不推荐 `ab`/`wrk`：无法方便地带 JSON body / Bearer 头 / 多场景权重。

### 方案 C（备选，暂不引入）：JMeter

仅当需要图形化编排/团队已有 JMeter 资产时再考虑；本项目场景 k6 全覆盖，且 JMeter 更重。

## 四、指标与通过阈值（开发机基线，非生产 SLO）

| 指标 | L0 只读 | L1 购物车 | L2 下单 | 说明 |
|---|---|---|---|---|
| P95 延迟 | < 300 ms | < 500 ms | < 800 ms | 单机+本地 MySQL+无缓存 |
| P99 延迟 | < 800 ms | < 1200 ms | < 2000 ms | |
| 错误率 | < 0.5% | < 0.5% | 业务外错误 < 0.5% | 下单的「库存不足」是**正常业务响应**，不计错误 |
| 超卖数 | — | — | **必须 = 0** | 一票否决项 |

- 加压模式：阶梯 10 → 30 → 50 → 100 vU，每档稳态 60s，观察 TPS 是否随 vU 线性增长（不再增长即到拐点）。
- 记录方式：方案 A 用 `System.nanoTime()` 分桶统计（勿用 `currentTimeMillis`）；方案 B k6 自动出。

## 五、数据准备与复位

1. **压测账号**：SQL 批量造 `139000xxxxx` 段手机号用户（或直接循环调 `sms-login` 自动注册），每 vU 绑定一个独立账号，避免购物车/订单互相干扰。
2. **秒杀商品**：专造 `status=1` 的 SKU，库存设大（如 10000）测吞吐；另设小库存（如 50）+ 100 并发复刻 `OversellConcurrencyTest` 验正确性。
3. **地址**：每账号先 `POST /api/v1/users/me/addresses` 造一条收货地址拿 `addressId`（下单必填）。
4. **复位**：压测后按 `users LIKE '139%'` 级联清理压测订单/购物车/地址，或压测前 `mysqldump` 快照、压测后恢复。**禁止**直接在含真实测试数据的库上重压下单接口而不做清理。
5. 观察项：压测期间盯 MySQL `SHOW PROCESSLIST` / 连接数、慢 SQL 日志。

## 六、已知环境坑（本机实测）

| 坑 | 对策 |
|---|---|
| `mvn` 在 Git Bash 直接调会失败 | 用 PowerShell 调 `mvn.cmd` |
| MySQL 是本地 3307 实例（datadir `C:/Windows/Temp/fruit-mysql/`） | 压测和 E2E 共用同库，压测时段不要跑 E2E，避免互相污染数据 |
| HikariCP 未配置，默认 **maximumPoolSize=10** | 高并发第一个瓶颈极大概率是连接池等待（Tomcat 默认 200 线程抢 10 连接）。压测报告应把「连接池等待时间」列为重点观察项；调优再改 `spring.datasource.hikari.maximum-pool-size` |
| 无 Redis | 列表/详情无缓存，QPS 上限由 DB 决定；这正好是引入缓存前的好基线 |
| Git Bash 路径 | 必须正斜杠 `/c/Users/季/Desktop/fruit` |
| 本机既是压测机又是服务机 | 结论只作相对基线；要对外数字需换独立压测机 |

- **第一期（方案 A，✅ 已完成）**：`backend/src/test/java/com/fruitmall/load/` 新增 `CartLoadTest`（购物车读+写并发）、`OrderCreateLoadTest`（大库存下单吞吐 + 小库存防超卖全链路）。运行命令：
  ```powershell
  & "C:\Users\季\Desktop\fruit\tools\apache-maven-3.9.9\bin\mvn.cmd" -o -f "C:\Users\季\Desktop\fruit\backend\pom.xml" test "-Dtest=CartLoadTest,OrderCreateLoadTest"
  ```
  实测发现并修复「订单号并发碰撞撞唯一索引」（`generateOrderNo` 随机 4 位改原子自增 6 位，见 `待优化项.md`）。结果与结论见下节。
- **第二期（方案 B）**：安装 k6，后端 `:8080` 常驻启动，跑 `fruit-load.js` 阶梯加压，拿完整 TPS 曲线与拐点。
- **第三期**：瓶颈定位与调优对照——开慢 SQL 日志、调 HikariCP 连接池、（可选）引入 Redis 缓存列表/详情，同脚本重压对比提升幅度。
- 每期产出追加到本文件「八、压测记录」。

## 八、压测记录

### 第一期（2026-08-31，方案 A 纯 Java，H2 内存库 test profile）

| 场景 | 并发 | 操作数 | TPS | avg | p50 | p95 | p99 | 错误 | 超卖 | 结论 |
|---|---|---|---|---|---|---|---|---|---|---|
| 购物车读写混合（加购→查→改→删） | 20 线程 | 1600 | 1397 | 11.33ms | 2.15ms | 56.04ms | 170.99ms | 0 | — | ✅ 零错误，p95 达标（<500ms） |
| 下单吞吐（库存 10000） | 20 线程 × 10 单 | 200 | 749 单/s | 22.04ms | 14.48ms | 61.35ms | 112.27ms | 0 | — | ✅ 修复订单号碰撞后全过 |
| 防超卖全链路（库存 50） | 100 线程 | 100 | 185 成功/s | 79.43ms | 76.06ms | 131.95ms | 135.74ms | 0 | 0 | ✅ 恰 50 成功、库存归零、明细恰 50 条 |

**执行结论**：
1. **发现并修复真缺陷**：`generateOrderNo()` 原为「秒级时间戳 + 4 位随机数」，200 单/秒即撞 `uk_order_no` 唯一索引（`DuplicateKeyException`，下单失败）。已改为原子自增 6 位序号，同 JVM 同秒容量 100 万单；DB 唯一索引保留兜底。
2. 防超卖在**完整下单事务链路**（不只是 mapper 单条 UPDATE）下依然成立：100 并发抢 50 库存，恰好 50 成功、50 次「库存不足」业务拦截、零未知异常、订单明细恰 50 条。
3. 数字是 H2 + 本机（客户端与服务端同机）基线，仅作**相对参考**；真实 MySQL 3307 + HTTP 层数字由第二期 k6 补充。
4. 已观察：下单 p50 明显高于购物车 p50（14.48ms vs 2.15ms），符合「事务 + 库存原子更新」的预期开销；高并发下 H2 偶发锁等待会推高 p95，需在 MySQL 上复核。

### 遗留备注

- 多实例部署时序号各自从 0 起，同秒跨实例仍可能碰撞订单号——上多实例需加实例标识或改雪花算法。
