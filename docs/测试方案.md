# 小程序端到端（E2E）测试方案

> 适用对象：果小满水果商城 uni-app 小程序（H5 模式）
> 配套可执行脚手架：`.workbuddy/test-miniapp.cjs`
> 配套可复用技能：`uniapp-h5-e2e-test`（已写入用户级 skills）
> 关联文档：[待优化项.md](./待优化项.md)（测试发现的问题汇总）

---

## 1. 背景与目标

小程序端（uni-app / Vue3）跑在微信 JSCore 里，很多 bug「开发者工具里正常、真机/预览才暴露」，且前端模板写错字段名不会报错、只会静默渲染空白。单纯靠 `node --check` 查语法、靠肉眼看截图，覆盖不到交互逻辑与「本地镜像 + 服务端」这类状态问题。

本方案的目标：
1. 用**真实浏览器**驱动运行中的 H5，对运行中的后端做端到端交互验证，替代纯静态检查。
2. 把验证手法沉淀成**可复用技能**与**可重复执行的脚本**，后续每次改动都能一键回归。
3. 通过测试**暴露真实缺陷**，并汇总成待优化清单。

---

## 2. 测试范围

| 模块 | 覆盖点 |
|------|--------|
| 购物车 | 加购、递减、删除、全选/单选、合计、空态推荐、隐身 id 渲染、跨端同步 |
| 登录态 | token 注入、退出登录清空本地态、清缓存保留登录态 |
| 商品详情 | 加入购物车（本地镜像写库） |
| 我的-派生页 | vip / service / help / settings / about 五页加载与关键文案 |
| 跨端一致性 | 服务端购物车同步进本地后的字段单位（价格）是否正确 |

**不在本方案范围**（环境/依赖未就绪，见[待优化项.md](./待优化项.md)）：
- 真机/微信开发者工具渲染（图标栅格化、真机白屏）—— 用 H5 模式等价验证逻辑。
- 微信支付真实链路（缺营业执照+商户号）。
- M3 秒杀（缺 Redis）。
- 后端单测（已有 53+ 用例，本方案聚焦前端 E2E）。

## 3. 环境准备

1. **后端**已起：`curl -m3 -o/dev/null -w "%{http_code}" http://localhost:8080/api/v1/auth/captcha` 返回 `200`。
2. **H5**已起：`cd miniapp && npm run dev:h5`，以日志 `Local: http://localhost:XXXX/` 的端口为准（5173/5175/5176/5177/5178 都可能，端口会被顺延）。
3. 全局装 `playwright-core`：`npm i -g playwright-core`（agent-browser 自带 Chromium 国内常被墙，勿走）。
4. 本机系统 Chrome：`C:/Program Files/Google/Chrome/Application/chrome.exe`。
5. 测试账号：开发模式万能短信码 `123456`，脚本 `getToken()` 自动用 `13800000000 / 123456` 换 token，无需手填。

---

## 4. 测试方法

核心思路：**模型看不到图，但能读 DOM 文本与组件内部状态**，所以验证靠两样：

- `page.evaluate(() => document.body.innerText)` —— 文本级核对页面是否渲染出关键文案。
- `page.evaluate(() => getCurrentPages()[getCurrentPages().length-1].$vm)` —— 直接读组件响应式数据（`cart` / `cartList` / `totalPrice` / `selected`），比解析 DOM 稳。

驱动方式：
- 用 `chromium.launch({ executablePath: 系统Chrome, args: ['--disable-web-security','--no-sandbox'] })`。
- `--disable-web-security` 绕过 H5(5178) → 后端(8080) 的 CORS（仅开发期便捷做法）。
- token 用 `page.addInitScript` 在文档最早期写进 `localStorage`，模拟已登录。
- 每个场景独立 `browser.newContext()`，存储互不污染。

> 完整踩坑与手法见技能 `uniapp-h5-e2e-test`。

## 5. 测试场景清单（含断言点）

脚本中每个场景对应一组 `record()` 断言；下表为人工可读版。

| 编号 | 场景 | 关键断言点 | 预期 |
|------|------|-----------|------|
| S1 | 本地加购与递减 | 详情页加购 3 次 → 本地存储 `qty=3`；购物车递减 3→2→1→移除 | 通过 |
| S2 | 隐身 id 回归 | 塞一个 PRODUCTS 没有的 `id=999` → 仍渲染「商品」且可递减 3→2→1→移除（回归「无法减少」修复） | 通过 |
| S3 | 全选 / 合计 | 两件商品渲染；合计 `5.9*2+8.8*1=20.60`；全选切换后合计归零 | 通过 |
| S4 | 空态推荐 | 空购物车显示「大家都在买」；点 + 一键加购后购物车非空 | 通过 |
| S5 | 跨端同步价格单位 | 登录后服务端购物车同步进本地，单价/合计应为「元」而非「分」 | 通过（曾为缺陷，已修复并作为回归护栏） |
| S6 | 五页加载 | vip/service/help/settings/about 含关键文案且无 console/pageerror | 通过（help 锚点已修正） |
| S7 | 清缓存保留登录态 | 清缓存确认后 token 仍在、本地购物车暂存被清 | 通过 |
| S8 | 退出登录 | 退出确认后本地 token 清空 | 通过 |

> S5 曾因真实缺陷失败：**后端购物车 `price` 为「分」，前端本地快照 `price` 为「元」，同步时直接写入导致价格 100×**（香蕉显示 ¥590、合计 ¥3150）。已在 `miniapp/src/utils/cart.js` 的 `syncFromServer` 改为 `price: it.price / 100` 修复，并重跑全量 29 条断言转绿。该场景现作为回归护栏，防止单位再次错位。详见 [待优化项.md](./待优化项.md) 的「一、本轮新发现并修复」。

## 6. 如何运行

```bash
# 跑全部场景（自动换 token）
node .workbuddy/test-miniapp.cjs

# 指定 H5 地址 / 直接给 token
BASE=http://localhost:5178 TOKEN=xxx node .workbuddy/test-miniapp.cjs

# 只跑部分（按场景名前缀匹配，逗号分隔）
SCEN=price,logout node .workbuddy/test-miniapp.cjs
```

- 结果打印 PASS/FAIL 汇总，并写入 `.workbuddy/test-report.json`（含每条断言的 expected/actual）。
- 任一断言失败，进程退出码非 0，可直接接 CI。

---

## 7. 结果判定与报告

- **PASS**：断言条件成立。
- **FAIL**：断言不成立，汇总区红字列出 `场景 / 断言名 / expected / actual`。
- 每个场景还附带「无 console/pageerror」断言，用来兜住运行时异常（如之前的 `URLSearchParams is not defined` 类崩溃）。
